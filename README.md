# linkd

Учебный сокращатель ссылок. Решения по неделям — ниже.

## D1 — anti-enumeration (неделя 3, день 1)

`short_code` больше не является base62-представлением автоинкрементного `id`: перед кодированием
`id` прогоняется через обратимую перестановку.

```
scramble(id) = (id · M) mod 2⁶⁴,   где M = 6364136223846793005
```

**Почему это перестановка, а не источник коллизий.** `M` нечётное, а значит взаимно просто с `2⁶⁴`.
У такого `M` существует обратный элемент по модулю `2⁶⁴`, следовательно умножение — биекция:
каждый `id` даёт уникальный результат, и преобразование теоретически обратимо. Уникальность
sequence сохраняется бесплатно — проверять коллизии в БД не нужно.

**Почему соседние `id` дают далёкие коды.** Умножение на большую константу размазывает изменение
младшего бита по всему 64-битному числу: `id=1000` и `id=1001` отличаются на 1, а их произведения —
на целое `M ≈ 6.3·10¹⁸`. Старшие биты, из которых лепится код, оказываются совершенно разными.
Тот же множитель используется в LCG-генераторе Кнута (MMIX).

**Ключевой момент реализации.** В Java умножение `long` молча переполняется по модулю `2⁶⁴` —
отдельного взятия остатка не требуется, переполнение и есть нужная арифметика.

Что это закрывает: последовательные коды позволяли перебрать всю базу инкрементом
(`/aaab`, `/aaac`, …) и выкачать чужие ссылки. После перестановки соседние коды не связаны, и
перебор вырождается в brute force по всему пространству.

## Q1 — где хранить idempotency (неделя 3, день 2)

Выбран **Postgres**, не Redis:

- Redis не гарантирует долговечность данных (может быть сброшен при перезапуске, падении,
  переполнении памяти), а idempotency-ключи должны храниться надёжно, чтобы избежать дублирования
  операций.
- Postgres обеспечивает транзакционность: запись в `links` и запись ответа в `idempotency`
  происходят в одной транзакции, поэтому невозможно состояние «ссылка создана, ключ не сохранён».
- Postgres банально проще — не нужен второй источник правды.

## D-решение — переиспользование кодов (неделя 3)

`short_code` уникален **глобально**, а не среди неистёкших ссылок (миграция `V8`). Истёкшая ссылка
не освобождает свой код.

Причина: переиспользование означает, что старый QR-код на визитке, ссылка в чате трёхлетней
давности или закладка в браузере внезапно начнут вести на чужой контент. Так же поступают
промышленные сокращатели — bit.ly никогда не выдаёт код повторно.

Рассмотренные альтернативы и почему отвергнуты:

- `CREATE UNIQUE INDEX ... WHERE expires_at > now()` — невозможно: предикат частичного индекса
  обязан быть `IMMUTABLE`, а `now()` помечена `STABLE`.
- Partial unique index по колонке-флагу `is_active` — требует фонового джоба и оставляет окно,
  где ссылка истекла, но флаг ещё не снят.
- `EXCLUDE USING gist (short_code WITH =, validity WITH &&)` — корректный темпоральный вариант,
  но тянет расширение `btree_gist` и более тяжёлый индекс ради семантики, которая здесь не нужна.
