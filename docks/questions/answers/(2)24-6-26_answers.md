# Ответы к вопросам по заметке (2) 24-6-26

**1. `CREATE INDEX CONCURRENTLY`.** Обычный `CREATE INDEX` берёт `SHARE`-блокировку: чтения проходят, запись в таблицу блокируется на всё время построения. `CONCURRENTLY` делает два прохода по таблице и ждёт завершения конкурирующих транзакций, беря лишь `SHARE UPDATE EXCLUSIVE` — запись не блокируется. Платы: работает заметно дольше, нагружает I/O, **не может выполняться внутри блока транзакции**, и при сбое оставляет индекс в состоянии `INVALID` (он не используется планировщиком, но занимает место). Лечение: `DROP INDEX CONCURRENTLY` и повторить, либо `REINDEX INDEX CONCURRENTLY`. Найти битые: `SELECT * FROM pg_index WHERE NOT indisvalid;`

**2. UNIQUE → B-tree.** PostgreSQL реализует уникальность через уникальный индекс: чтобы проверить «нет ли уже такого значения», нужна быстрая структура поиска, и B-tree ей и является. Поэтому отдельный индекс на `short_code` создавать не надо — он уже есть, и по нему прекрасно работает поиск при редиректе. Обратный приём для zero-downtime: сначала `CREATE UNIQUE INDEX CONCURRENTLY uq_idx ON links(short_code);`, затем `ALTER TABLE links ADD CONSTRAINT links_short_code_key UNIQUE USING INDEX uq_idx;` — второй шаг мгновенный.

**3. Constraint vs index.** UNIQUE constraint — объект логической схемы (виден в `information_schema`, на него можно ссылаться из FK, он нужен для `ON CONFLICT ON CONSTRAINT`). UNIQUE index — физическая структура. Constraint нельзя сделать частичным или по выражению; уникальный **индекс** — можно: `CREATE UNIQUE INDEX ON links(short_code) WHERE deleted_at IS NULL;` или `CREATE UNIQUE INDEX ON users(lower(email));`. Именно поэтому для мягкого удаления и регистронезависимой уникальности берут индекс, а не constraint.

**4. `nextval()` и дыры.** Последовательность — отдельный объект со своим состоянием, изменения которого **не откатываются** транзакцией. Это сознательный компромисс: иначе каждый вызов сериализовал бы все конкурирующие транзакции. Как следствие, `ROLLBACK` не возвращает номер обратно, и в колонке появляются пропуски. Дыры также создаёт кэширование (`CACHE n` выдаёт сессии диапазон, остаток теряется при её закрытии) и Hibernate-овский `allocationSize`. Вывод: sequence гарантирует уникальность и возрастание, но **не** непрерывность — на неё нельзя опираться в бизнес-логике (например, для нумерации документов).

**5. IDENTITY vs SEQUENCE.** IDENTITY: Hibernate обязан выполнить `INSERT ... RETURNING id` немедленно при `persist()`, потому что до вставки id неизвестен, а без id объект нельзя положить в persistence context. Отсюда главный минус — **JDBC-батчинг отключается**: нельзя накопить 100 INSERT'ов и отправить пачкой, если после каждого нужно читать сгенерированный ключ. SEQUENCE: `SELECT nextval(...)` до вставки, id известен заранее, `INSERT` откладывается до flush и отлично батчится. Для массовой записи SEQUENCE строго лучше.

**6. `allocationSize` и оптимизаторы.** `allocationSize = 50` означает: Hibernate вызывает `nextval` один раз, получает N и раздаёт из памяти 50 идентификаторов, экономя 49 обращений к БД. Условие корректности — в БД должно быть `INCREMENT BY 50`. Если в БД `INCREMENT BY 1`, а в коде 50, Hibernate начнёт раздавать id, которые последовательность выдаст позже другому клиенту → конфликты по PK. Оптимизаторы: `pooled` (Hibernate трактует значение как верхнюю границу диапазона), `pooled-lo` (как нижнюю) — `pooled-lo` безопаснее при совместной работе с внешними писателями в ту же таблицу. Настройка: `hibernate.id.optimizer.pooled.preferred`.

**7. BY DEFAULT vs ALWAYS.** `GENERATED ALWAYS AS IDENTITY` запрещает вставлять свой id — попытка упадёт с ошибкой, обойти можно только `INSERT ... OVERRIDING SYSTEM VALUE`. `GENERATED BY DEFAULT` подставляет значение из последовательности, только если id не указан явно. Второй вариант нужен, когда id иногда приходит извне: миграция данных, импорт, тесты с фикстурами, а также сценарий из заметки — Hibernate с `SEQUENCE` сам получает id и передаёт его в `INSERT` явно. Ловушка `BY DEFAULT`: ручные вставки не двигают последовательность, и позже она начнёт выдавать занятые номера — приходится делать `setval()`.

**8. Redis INCR.** Атомарен, потому что Redis исполняет команды в одном потоке — между чтением и записью никто не вклинится; `INCR` на несуществующем ключе создаёт его со значением 1. Риски: при рестарте без персистентности счётчик обнулится и выданные ранее id пойдут по второму кругу. Смягчение: AOF с `appendfsync everysec` (в худшем случае теряется секунда) и/или периодическое сохранение «высокой отметки» в PostgreSQL, откуда счётчик восстанавливается с запасом. `INCRBY key 1000` даёт инстансу целый диапазон разом — один сетевой вызов на 1000 ссылок, ценой дыр при рестарте инстанса. Учтите, что при failover на реплику (асинхронная репликация) счётчик может откатиться — для строгой гарантии нужен свой источник в БД.

**9. Detached entity в Hibernate 7.** `persist()` требует, чтобы объект был **transient** — новым, ещё не имеющим идентичности в БД. Признак `isNew` Spring Data определяет по `null`-ности id (или через `Persistable`). Когда стоит `@GeneratedValue(SEQUENCE)`, Hibernate считает, что id — его зона ответственности; увидев непустой id у объекта, переданного в `persist()`, он делает вывод, что объект уже когда-то был сохранён и «отцепился» от сессии → `PersistentObjectException: detached entity passed to persist`. Варианты решения: (а) не заполнять id вручную и довериться генератору; (б) снять `@GeneratedValue`, как в заметке — тогда id полностью в вашей власти, но нужно реализовать `Persistable.isNew()`, иначе Spring Data вызовет `merge()`, а тот сделает лишний `SELECT` перед `INSERT`; (в) `entityManager.merge()`, но он возвращает **другой** экземпляр — управляемую копию — и это частый источник багов.

**10. Flyway.** Таблица `flyway_schema_history` хранит по строке на применённую миграцию: версию, описание, checksum, время, флаг успеха. При старте Flyway сверяет файлы на classpath с историей: новые версии применяет по порядку, для уже применённых сверяет checksum. Правка применённого файла ломает checksum → `FlywayValidateException` и приложение не поднимется. Правильный выход — новая миграция `V5__fix_previous.sql`; `flyway repair` (пересчёт checksum) уместен только когда вы точно знаете, что схема в БД соответствует новому содержимому файла, — типично после отката неудачного релиза. Никогда не редактируйте миграцию, уехавшую в общую ветку.

**11. Индекс на живой таблице + Flyway.** `CREATE INDEX CONCURRENTLY` не может выполняться внутри транзакции, а Flyway по умолчанию оборачивает каждую миграцию в транзакцию. Решение: положить его в отдельный файл и отключить транзакцию — в Flyway это конфиг `flyway.executeInTransaction=false` или аннотация на скрипте (в новых версиях `-- flyway:executeInTransaction=false` в шапке файла). Liquibase — `runInTransaction="false"`. Альтернатива для больших таблиц — вообще вынести создание индекса из деплой-пайплайна в ручную операцию DBA.

**12. Типы индексов.** B-tree — универсальный, для `=`, `<`, `>`, `BETWEEN`, `ORDER BY`, префиксного `LIKE 'abc%'`. Hash — только `=`, чуть компактнее, но выигрыш редко оправдывает потерю универсальности. GIN — для составных значений: `jsonb`, массивы, полнотекстовый поиск, а с `pg_trgm` — для `LIKE '%abc%'`. GiST — геометрия, диапазоны, поиск по близости. BRIN — крошечный индекс для очень больших таблиц с физически упорядоченными данными (логи по времени вставки): идеален для `created_at` в append-only таблице кликов.

**13. Читаем план.** `EXPLAIN (ANALYZE, BUFFERS) SELECT ...` показывает и оценку, и факт. `Seq Scan` — полный проход (нормально для маленьких таблиц, тревожно для больших). `Index Scan` — поиск по индексу плюс поход в heap за остальными колонками. `Index Only Scan` — всё нужное лежит в индексе, heap не читается (работает благодаря visibility map, поэтому зависит от свежести `VACUUM`). Сигналы проблем: большая разница между `rows=` оценкой и `actual rows` (устаревшая статистика → `ANALYZE`), высокие `Rows Removed by Filter`, `Bitmap Heap Scan` с большим `Recheck`.

**14. Почему не публиковать инкрементный ID.** Base62 от последовательного счётчика даёт легко перебираемое пространство: злоумышленник обходит все ссылки инкрементом, а разница между кодами, полученными в разное время, раскрывает темпы роста сервиса (enumeration + business intelligence leak). Альтернативы: случайный код из 7–8 символов Base62 с проверкой уникальности (при 62^7 ≈ 3,5·10^12 коллизии редки, а ограничение БД их ловит); хэш от URL+соль с усечением; Snowflake (время + машина + счётчик, монотонный, но всё ещё предсказуемый); ULID/UUIDv7 — сортируемые, но длинные для короткой ссылки. Компромисс на практике: случайный код + retry на конфликте.

**15. Генерация без гонок на нескольких инстансах.**
- *Sequence в БД*: проще всего, строгая уникальность, но сетевой round-trip на каждую ссылку (снимается `allocationSize`), единая точка отказа — сама БД, которая и так у вас есть.
- *Redis INCR*: быстрее, снимает нагрузку с БД, но добавляет зависимость и риск отката счётчика при failover.
- *Отдельный сервис-генератор*: полный контроль, но это ещё один сервис в эксплуатации — оправдано только на большом масштабе.
- *Range allocation (hi/lo)*: инстанс берёт диапазон 1000 значений разом и раздаёт из памяти. Один round-trip на 1000 ссылок, зато дыры при рестарте. Практически это лучший баланс, и именно так работает Hibernate `pooled`.
