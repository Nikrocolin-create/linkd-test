# Ответы к вопросам по заметке (3) 27-6-26

**1. `ALTER TABLE ... ADD CONSTRAINT UNIQUE`.** Упадёт, если в таблице уже есть дубликаты (`could not create unique index ... Key (email)=(...) is duplicated`) — сначала нужно их вычистить. Блокировка — `ACCESS EXCLUSIVE`: на время построения индекса таблица недоступна даже для чтения. 
Безопасный вариант в два шага:
```sql
CREATE UNIQUE INDEX CONCURRENTLY uq_users_email ON users(email);
ALTER TABLE users ADD CONSTRAINT uq_users_email UNIQUE USING INDEX uq_users_email;
```
Второй шаг мгновенный — PostgreSQL просто «усыновляет» готовый индекс.

**2. Почему `try-catch` не ловит.** Ровно как в заметке: `repository.save()` в рамках `@Transactional` только помещает сущность в persistence context (first-level cache) и планирует INSERT. Реального SQL ещё нет — ловить нечего. SQL уходит в БД при flush, который для `save()` без явного `flush()` случается на коммите транзакции, то есть **после** выхода из метода, когда прокси `@Transactional` завершает транзакцию. Исключение возникает уже за пределами вашего `try`, и наружу оно летит как `DataIntegrityViolationException` (обёрнутое `TransactionSystemException`, если это произошло в commit).

**3. `FlushModeType.AUTO`.** Дефолт. Hibernate делает flush: (а) перед `commit`; 
(б) перед выполнением JPQL/HQL/Criteria-запроса, результат которого может зависеть от накопленных изменений (Hibernate проверяет пересечение затрагиваемых таблиц); 
(в) при явном `flush()`. Важная деталь: **нативные SQL-запросы** этой эвристикой не покрываются надёжно — Hibernate не всегда понимает, 
какие таблицы они трогают, отсюда классический баг «нативный запрос не видит только что сохранённые данные». `FlushModeType.COMMIT` отключает промежуточные flush'и совсем.

**4. Что делает `flush()` и чем заменить.** `flush()` принудительно выгружает накопленный SQL в БД в текущей транзакции — исключение прилетит здесь и попадёт в ваш `try-catch`. Это не то чтобы костыль, но «дырявая абстракция»: код начинает зависеть от момента синхронизации с БД. Варианты:
- `saveAndFlush()` — то же самое, но честнее выглядит;
- ловить `DataIntegrityViolationException` уровнем выше, на границе транзакции (в сервисе-обёртке или в `@ControllerAdvice`);
- при генерации short_code — цикл ретраев: сгенерировать код, попытаться вставить, при конфликте сгенерировать новый (обычно достаточно 3 попыток);
- `INSERT ... ON CONFLICT DO NOTHING` нативным запросом и проверка числа затронутых строк — минимум round-trip'ов.

Важно: после исключения внутри транзакции persistence context в неконсистентном состоянии, и транзакция помечена rollback-only — продолжать работать в ней нельзя. 
Ретрай должен идти в **новой** транзакции (`REQUIRES_NEW` или ретрай на уровне вызывающего кода).

**5. Почему `SELECT`-then-`INSERT` не спасает.** Классический TOCTOU: два потока делают `SELECT`, оба видят «свободно», оба вставляют. 
На `READ COMMITTED` они даже не заблокируют друг друга на этапе чтения. Единственный по-настоящему атомарный арбитр — уникальный индекс в БД: 
он проверяет и вставляет неразрывно. Отсюда общий принцип: **проверка в коде — это оптимизация UX (красивое сообщение об ошибке), 
корректность обеспечивает только ограничение в БД.** Убирать constraint, положившись на проверку в приложении, нельзя.

**6. Трансляция исключений.** JDBC-драйвер бросает `SQLException` с SQLState (`23505` — unique violation, `23503` — foreign key violation, `23502` — not null). 
Hibernate оборачивает это в свой `ConstraintViolationException` (не путать с одноимённым классом из Bean Validation!)
, а Spring через `SQLExceptionTranslator` / `PersistenceExceptionTranslationPostProcessor` (активен благодаря `@Repository`) переводит в иерархию 
`DataAccessException`: `DuplicateKeyException` (наследник `DataIntegrityViolationException`) для 23505, `DataIntegrityViolationException` для FK. 
Различить точно: спуститься к причине и посмотреть `getConstraintName()` у Hibernate-овского исключения или SQLState у 
`PSQLException` — по имени ограничения можно выдать пользователю осмысленное сообщение.

**7. `webEnvironment`.**
- `MOCK` (по умолчанию) — реальный сервер не поднимается, есть мок сервлет-окружения, работать через `MockMvc`.
- `RANDOM_PORT` — поднимается настоящий встроенный Tomcat на свободном порту; порт доступен через `@LocalServerPort`. Тест ходит по реальному HTTP — проверяются сериализация, фильтры, конвертеры, коды статусов «по-честному».
- `DEFINED_PORT` — реальный сервер на порту из конфига; плохо для CI (конфликты портов, параллельные запуски).
- `NONE` — контекст без веб-окружения.

`@WebMvcTest` достаточно, когда тестируется только слой контроллера: 
поднимается урезанный контекст (контроллеры, advice, конвертеры), сервисы заменяются на `@MockitoBean`. Он на порядок быстрее полного `@SpringBootTest`.

**8. `TestRestTemplate`.** Обёртка вокруг `RestTemplate` с тестовыми удобствами:
(а) не бросает исключений на 4xx/5xx — возвращает `ResponseEntity` со статусом, что позволяет ассертить ошибки без `try-catch`; 
(б) авто-конфигурируется с `baseUrl`, указывающим на `RANDOM_PORT` (потому и не нужно вручную подставлять порт); 
(в) умеет basic auth через `withBasicAuth()`; (г) **не следует за редиректами** по умолчанию — критично для тестирования короткой ссылки: вы проверяете именно 302 и заголовок `Location`, а не конечную страницу. `WebTestClient` — современная альтернатива с fluent-ассертами, работает и с MVC, и с WebFlux; для нового кода обычно берут его.

**9. Location header.** `fromCurrentRequest()` берёт URI текущего запроса (схема, хост, порт, путь), `.path("/{id}")` дописывает сегмент, 
`buildAndExpand(id)` подставляет переменную, `.toUri()` собирает результат. `ResponseEntity.created(location)` — это `201 Created` + заголовок `Location`. 
Семантика REST: на успешное создание ресурса возвращают 201 и адрес созданного ресурса, тело опционально (часто отдают представление созданного объекта). 
За reverse proxy `fromCurrentRequest()` увидит внутренний адрес (`http://localhost:8080/...`) и отдаст клиенту неработающую ссылку. 
Лечение: `server.forward-headers-strategy=framework` (включает `ForwardedHeaderFilter`) или `=native`, 
если проксирование обрабатывает сам контейнер; прокси при этом обязан проставлять `X-Forwarded-Proto/Host/Port`. 
Принимать эти заголовки можно только от доверенного прокси — иначе клиент подделает `Location`.

**10. Batch-удаление протухших ссылок.** Один `DELETE FROM links WHERE expires_at < now()` на миллионах строк — долгая транзакция, раздувание WAL, блокировки, риск таймаута и полного отката всей работы. Правильнее — порциями:
```sql
DELETE FROM links WHERE id IN (
  SELECT id FROM links WHERE expires_at < now() LIMIT 1000 FOR UPDATE SKIP LOCKED
);
```
в цикле, пока затронутых строк > 0, каждая итерация — своя транзакция, между итерациями небольшая пауза. `SKIP LOCKED` позволяет нескольким инстансам работать параллельно без взаимных блокировок. Запуск — `@Scheduled(cron = "0 0 3 * * *")`. На нескольких инстансах, чтобы задача выполнялась один раз, нужен распределённый лок — ShedLock (`@SchedulerLock`) поверх той же PostgreSQL или Redis. Альтернативы самому удалению: партиционирование по времени с `DROP PARTITION` (мгновенно, без раздувания) или мягкое удаление + отдельная фоновая чистка. Не забыть про `VACUUM` — DELETE не освобождает место на диске сам по себе.

**11. CDC и Debezium.** Change Data Capture — чтение потока изменений данных вместо периодического опроса таблиц. 
Для PostgreSQL Debezium использует логическую репликацию: создаёт replication slot, читает WAL через плагин (`pgoutput`) 
и превращает записи в события `{before, after, op, source}`, которые публикует в Kafka — топик на таблицу. Для MongoDB — change streams (поверх oplog), 
с возобновлением по resume token. Ключевое преимущество перед polling: нет нагрузки на таблицы, ловятся удаления, порядок событий сохраняется. 
Ключевая опасность PostgreSQL-слота: если консьюмер остановился, WAL **не удаляется** и диск может кончиться — обязателен мониторинг лага слота.

**12. Гарантии и outbox.** Debezium даёт **at-least-once**: после сбоя часть событий может прийти повторно, поэтому потребитель обязан быть идемпотентным — дедупликация по (source LSN / resume token) или upsert по натуральному ключу вместо insert. Exactly-once в общем случае недостижим сквозь всю цепочку (Kafka transactions дают его только внутри Kafka). Transactional outbox: вместо «записать в БД и отправить в Kafka» (две операции без общей транзакции — при падении между ними данные разъезжаются) пишут в таблицу `outbox` **в той же транзакции**, что и бизнес-данные, а CDC/отдельный релей публикует записи из неё. Так атомарность обеспечивает сама БД. Debezium даже имеет готовый Outbox Event Router.

**13. Уровни изоляции PostgreSQL.** `READ UNCOMMITTED` в PostgreSQL отсутствует (ведёт себя как READ COMMITTED). 
`READ COMMITTED` (дефолт): каждый оператор видит снимок на момент своего старта — возможны non-repeatable read и phantom read внутри транзакции. 
`REPEATABLE READ`: снимок фиксируется на момент старта транзакции; в PostgreSQL благодаря MVCC он заодно исключает и фантомы, но появляются ошибки сериализации (`40001`) 
при конкурентных обновлениях. `SERIALIZABLE`: полная сериализуемость через SSI, ещё больше `40001`. 
Практика: 99% CRUD прекрасно живёт на READ COMMITTED плюс ограничения в БД. Уровень выше нужен, когда решение принимается на основе прочитанного 
и записывается обратно (списание баланса, резервирование мест) — и тогда обязателен ретрай на `40001`. 
Часто дешевле обойтись пессимистичной блокировкой `SELECT ... FOR UPDATE` на конкретной строке.

**14. Self-invocation и приватные методы.** Spring реализует `@Transactional` через прокси: контейнер подсовывает бинам не ваш объект, 
а обёртку (JDK-прокси по интерфейсу или CGLIB-наследника), которая открывает транзакцию и делегирует вызов. 
Когда метод бина вызывает другой метод **того же** объекта через `this`, вызов идёт мимо прокси — аннотация игнорируется молча, без предупреждения. 
То же с `private`/`final` методами: CGLIB не может их переопределить. Решения: вынести метод в отдельный бин; инжектировать сам себя (`@Lazy self`); 
`AopContext.currentProxy()` (требует `exposeProxy = true`); либо AspectJ weaving, который работает на уровне байткода и лишён этой проблемы. 
Аналогично ломаются `@Cacheable`, `@Async`, `@Retryable`.

**15. Testcontainers.**
```java
@Testcontainers
@SpringBootTest(webEnvironment = RANDOM_PORT)
class LinkIT {
    @Container @ServiceConnection
    static PostgreSQLContainer<?> db = new PostgreSQLContainer<>("postgres:16-alpine");
}
```
`@ServiceConnection` (Boot 3.1+) сам прописывает url/username/password — `@DynamicPropertySource` больше не нужен, хотя остаётся вариантом для нестандартных случаев. Контейнер лучше делать `static`, чтобы он поднимался один раз на класс; для всего набора тестов — singleton-контейнер в базовом классе или Testcontainers reuse (`testcontainers.reuse.enable=true`), иначе тесты будут ползти.

Изоляция данных: `@Transactional` на тесте с откатом после — быстро, но **не работает** с `RANDOM_PORT`, потому что запрос обрабатывается в другом потоке и своей транзакции; там нужна явная очистка (`TRUNCATE ... CASCADE` в `@AfterEach`, `@Sql`-скрипты или пересоздание схемы Flyway'ем). Отдельно проверьте, что миграции Flyway применяются к контейнеру — это заодно даёт бесплатный тест самих миграций.
