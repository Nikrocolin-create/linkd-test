--- 1. Что физически делает INSERT ... ON CONFLICT ---

Это не "проверь и вставь", а speculative insertion:
  1) вставляет спекулятивный кортеж в heap
  2) идёт вставлять запись в уникальный индекс
  3) находит конфликт и смотрит на транзакцию-владельца конфликтующей записи:
       - закоммичена  -> конфликт настоящий, идём в DO UPDATE
       - откатилась   -> конфликта нет, вставка проходит
       - ЕЩЁ ОТКРЫТА  -> угадать нельзя, БЛОКИРУЕМСЯ на XID-локе (XactLockTableWait)

Третий случай — логическая необходимость, а не политика блокировок. Уникальное
ограничение = инвариант "не больше одной живой строки с данным id". Пропустить
нельзя (вдруг тот закоммитится), отказать нельзя (вдруг откатится). Остаётся ждать.
Ни одна СУБД с unique constraint не может поступить иначе.

Ждут только ПИСАТЕЛИ ЗА ПИСАТЕЛЯМИ ПО ОДНОМУ И ТОМУ ЖЕ КЛЮЧУ.
  - разные Idempotency-Key -> никакого ожидания, идут параллельно
  - победитель уже закоммичен -> ожидания нет, сразу видно строку
  - SELECT (findById) НИКОГДА не ждёт незакоммиченную строку: MVCC просто её
    не покажет. Читатели не блокируют писателей и наоборот.

Уровень изоляции не спасает: изоляция про видимость при ЧТЕНИИ, а тут конфликт
запись-против-записи. READ COMMITTED -> заблокируется и продолжит.
REPEATABLE READ / SERIALIZABLE -> заблокируется и получит could not serialize access.
Управляют ожиданием только таймауты: lock_timeout (по умолчанию 0 = ждать вечно)
и statement_timeout.

Проверить руками, 5 минут, два окна psql:
  сессия 1: BEGIN; <INSERT из claim с новым UUID>;   -- не коммитить, вернёт INSERT 0 1
  сессия 2: тот же INSERT                            -- ПОВИСНЕТ
  сессия 3: SELECT pid, state, wait_event_type, wait_event, query
              FROM pg_stat_activity WHERE wait_event_type = 'Lock';
            -> сессия 2 с wait_event = 'transactionid'
  сессия 1: COMMIT;  -> сессия 2 мгновенно вернёт INSERT 0 0


--- 2. Главный вывод дня: работал не тот механизм, который написан ---

Пока claim жил внутри @Transactional метода create, происходило вот что:

  t1  A: claim -> INSERT ок, вернулось 1. Строка IN_PROGRESS есть, НЕ закоммичена
  t2  B: claim -> конфликт, владелец = открытая tx A -> БЛОКИРОВКА, поток висит
  t3  A: nextId, save(link), Redis, idempotencySave -> status=DONE
  t4  A: COMMIT
  t5  B: разблокировался, DO UPDATE, WHERE expires_at < now() -> false -> вернулось 0
  t6  B: findById -> видит DONE -> вернул ответ победителя

Сценарий работал — но за счёт строки t2, обычной блокировки на PK. Не за счёт
lease, не за счёт статусов, не за счёт WHERE. Написан протокол координации, а
координацию делал Postgres, на шаг раньше.

Ветка ожидания (sleep + повторное чтение) была НЕДОСТИЖИМА. Чтобы туда попасть,
нужно одновременно: claim вернул 0 И статус не DONE. Откуда взяться закоммиченной
строке не-DONE?
  - IN_PROGRESS? Не бывает. Он существует только внутри открытой tx победителя,
    а к её коммиту idempotencySave уже перевёл в DONE — это одна транзакция.
  - Победитель упал? Откатывается ВСЯ tx вместе с claim. Строки нет, конкурент
    получит 1, а не 0.
  - NULL? Единственный реальный путь, закрыт миграцией с DEFAULT 'DONE'.

Следствие: lease тоже был мёртв. WHERE expires_at < now() — правило "перехватить
брошенную аренду", но брошенных аренд не бывает. А когда условие станет истинным
(ссылка с коротким ttl), это сработает не как спасение, а как ПЕРЕЗАХВАТ
завершённого ключа с созданием второй ссылки. Единственный путь, где lease
оживает сегодня — это баг.

Цена случайного механизма: это сериализация, а не coalescing. N запросов с одним
ключом -> 1 работает, N-1 висят, каждый держит поток Tomcat и коннект Hikari,
ждут ровно столько, сколько работает победитель, и по умолчанию БЕСКОНЕЧНО
(lock_timeout=0). А если lock_timeout настроить — конкурент получит не 409,
а CannotAcquireLockException, то есть 500.


--- 3. Роль @Transactional: не факт блокировки, а её длительность ---

@Transactional НЕ создаёт блокировку. Она возникла бы и без него. Аннотация
определяет, как долго победитель держит незакоммиченную запись в индексе:

  было (claim внутри create):  окно = весь метод, десятки-сотни мс
  стало (REQUIRES_NEW):        окно = один INSERT, ~1 мс

REQUIRES_NEW не устраняет блокировку на PK — она никуда не делась и продолжает
защищать инвариант уникальности. Он сжимает её до незаметной. Именно поэтому
после рефакторинга протокол (статусы, опрос, lease, 409) наконец включился.


--- 4. Грабли Spring, на которые наступил ---

а) Self-invocation. Вызов @Transactional(REQUIRES_NEW) метода того же бина через
   this идёт МИМО прокси, аннотация молча игнорируется. Поэтому claim вынесен в
   отдельный бин IdempotencyService, а не оставлен приватным методом LinkService.

б) @Modifying требует активную транзакцию.
   Ошибка: TransactionRequiredException: No active transaction for update or delete query
   Заблуждение "репозитории Spring Data сами транзакционные" верно наполовину.
   SimpleJpaRepository помечен @Transactional(readOnly=true) на уровне КЛАССА, и это
   работает для ЕГО СОБСТВЕННЫХ методов: save, deleteById, findById.
   Но метод, ОБЪЯВЛЕННЫЙ НА ИНТЕРФЕЙСЕ с @Query, реализации в SimpleJpaRepository
   не имеет — class-level аннотация к нему НЕ применяется.
   Правило: @Modifying-метод обязан получить транзакцию либо от вызывающего кода,
   либо от аннотации на себе.
   Отсюда: deleteById не падал (родной метод), readResult не падал (чтение),
   tryClaim падал (свой @Query + нетранзакционный LinkManager).

в) Кэш первого уровня Hibernate. Два findById по одному id В ОДНОЙ ТРАНЗАКЦИИ ->
   второй вернёт ту же сущность из persistence context, В БД НЕ ПОЙДЁТ. Опрос
   чужого прогресса изнутри своей транзакции не работает в принципе: статус
   навсегда останется тем, каким прочитался в первый раз.
   Лечение: каждый опрос — своя транзакция (цикл вне транзакции, в LinkManager).

г) REQUIRES_NEW при отсутствии внешней транзакции == REQUIRED. Оркестратор
   нетранзакционный, так что сейчас это просто страховка на будущее.


--- 5. Что ломает вынос claim в отдельную транзакцию ---

Раньше откат бизнес-логики уносил claim с собой (одна транзакция). Теперь claim
закоммичен отдельно и ПЕРЕЖИВАЕТ откат.

Сценарий: занятый alias -> DataIntegrityViolationException -> tx create
откатывается -> строка IN_PROGRESS ОСТАЁТСЯ. Клиент получил 409 "alias exists",
повторяет с тем же ключом — и пока не истёк lease получает 409 "idempotency
timeout". Другая ошибка про другое.

Право снять claim есть ТОЛЬКО У ВЛАДЕЛЬЦА — в ветке, где tryClaim вернул true,
а create бросил. У ожидающего таких прав НЕТ (иначе он снесёт строку победителя,
и третий запрос создаст вторую ссылку).

Развилка на будущее (записать решение в README):
  - удалять claim при ошибке — просто, но при падении процесса спасёт только lease
  - статус FAILED + запоминание ошибки, отдавать её на ретрай — так делает Stripe


--- 6. Постгресовые мелочи, которые ещё аукнутся ---

now() в Postgres — это время НАЧАЛА ТРАНЗАКЦИИ, а не текущий момент. Ждущий
провисел на блокировке 200 мс — его now() остался старым. Настоящее текущее время
внутри транзакции даёт clock_timestamp().

Instant.now() в Java против now() в SQL — часы JVM и БД могут разъехаться
(разные хосты, контейнеры, дрейф NTP). Lease считать полностью на стороне БД.

Миграция: DEFAULT нужен ровно один раз, для backfill.
  ALTER TABLE ... ADD COLUMN status varchar(15) DEFAULT 'DONE' NOT NULL;
  ALTER TABLE ... ALTER COLUMN status DROP DEFAULT;   <- иначе будущий INSERT без
  status молча станет DONE, а response после DROP NOT NULL уже nullable ->
  клиент получит null вместо ответа.

Flyway: правка УЖЕ ПРИМЕНЁННОЙ миграции = checksum mismatch на старте. Testcontainers
поднимает чистую базу и этого не поймает, локальный запуск упадёт.
Лечение: flyway repair или снести локальную БД.
