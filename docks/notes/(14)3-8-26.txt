--- 1. ГЛАВНОЕ: Open Session In View ломает опрос ---

spring.jpa.open-in-view = true ПО УМОЛЧАНИЮ (Spring Boot пишет об этом WARN на
каждом старте — тот самый, который все листают).

Что делает: привязывает ОДИН EntityManager ко ВСЕМУ HTTP-запросу, чтобы ленивые
связи можно было подгружать во вью-слое.

Побочный эффект: persistence context живёт весь запрос, а НЕ транзакцию.
Значит кэш первого уровня переживает границы транзакций.

Как это выстрелило: readResult нетранзакционный, рассчитывали, что каждый
findById получит свой короткий EntityManager и сходит в БД. С OSIV они делят
один — второй и последующие findById возвращают ТУ ЖЕ управляемую сущность
БЕЗ ЕДИНОГО SELECT.

Итог в тесте на гонку (20 потоков, один ключ): 11 x 201 и 9 x 409.
  - поток, чей ПЕРВЫЙ readResult попал в окно IN_PROGRESS, залипал на
    IN_PROGRESS НАВСЕГДА. Пять опросов за секунду — пять раз одна и та же
    копия из памяти. Выжигал бюджет и отдавал 409.
  - поток, чей первый readResult пришёл после коммита победителя, сразу
    видел DONE и возвращал 201.
Цикл опроса физически НЕ ОПРАШИВАЛ.

Лечение: spring.jpa.open-in-view: false  -> 8/8 зелёных.
Отключать стоит и вне этой истории: OSIV размывает границы персистентного
контекста, запросы к БД уезжают за пределы сервисного слоя.

ВАЖНО ЗАПОМНИТЬ: "нетранзакционный вызов = свежее чтение" НЕВЕРНО, пока OSIV
включён. Транзакционные границы и границы persistence context — разные вещи.
Это та же ловушка L1-кэша из конспекта 1-8, вернувшаяся через другую дверь.


--- 2. @Transactional timeout — В СЕКУНДАХ ---

@Transactional.timeout() объявлен как int и трактуется как СЕКУНДЫ
(TransactionDefinition#getTimeout() — "timeout in seconds").
timeoutString — та же величина, просто резолвится из property.

Написал creation_transaction_ms: 800 — получил 800 СЕКУНД (13 минут), то есть
защиты не было вообще.

Следствие: под-секундный бюджет через @Transactional выразить НЕЛЬЗЯ,
гранулярность — целые секунды. Нужны миллисекунды — только statement_timeout.

Как проверил, не трогая файлы (полезный приём):
  контроль:  -Dconfig.creation_transaction_ms=abc
             -> "Invalid timeoutString value; NumberFormatException"
             значит property реально доезжает до аннотации и парсится в int
  опыт:      -Dconfig.creation_transaction_ms=1  -> 7/7 зелёных
             будь это мс, транзакция с бюджетом 1 мс не выжила бы нигде
Вывод: секунды.


--- 3. lease vs retention: одна колонка, значение зависит от состояния ---

expires_at несёт РАЗНЫЙ смысл в разных состояниях, и это нормально:
  IN_PROGRESS -> lease     (докуда действует аренда)      пишет tryClaim
  DONE        -> retention (докуда хранится ключ)         пишет idempotencySave
Условие WHERE expires_at < now() в claim остаётся ОДНО и корректно в обоих
случаях: подхватывает брошенную аренду и освобождает протухший ключ.

Ошибка, которую сделал: записал retention (24 ч) в состояние IN_PROGRESS.
Тогда убитый процесс блокирует ключ на СУТКИ вместо секунд.

Требования у величин ПРОТИВОПОЛОЖНЫЕ:
  lease     — как можно КОРОЧЕ (быстрое восстановление), но длиннее обработки
  retention — как можно ДЛИННЕЕ (окно дедупликации), сутки
Одной константой оба вопроса не закрыть по построению.

Цепочка неравенств, каждое звено обязательно:
  retention 86400s >> lease 5s > create timeout 3s > max_wait 1s > poll 200ms
  lease > create timeout  — владелец не может пережить свою аренду,
                            и это ГАРАНТИРУЕТСЯ таймаутом, а не надеждой


--- 4. Тест на гонку: как писать ---

Скелет — как в simultaneousRequestsCacheHitMissTets.

  CountDownLatch startGate — без него потоки стартуют вразнобой: пока submit
    дойдёт до двадцатого, первый уже закоммитится и гонки не будет
  пул ровно на n потоков — меньше, и часть задач попадёт на готовый DONE
  Callable<Result> с возвратом (status, body), а НЕ andExpect внутри потока:
    иначе ассерт падает в воркере, JUnit покажет ExecutionException, а причина
    ("19 из 20 вернули 409") утонет в обёртках. Возвращаем данные — проверяем
    на главном потоке
  UUID.randomUUID() для ключа — база общая с локальным запуском, захардкоженный
    ключ на втором прогоне вернёт DONE из прошлого раза и тест позеленеет,
    ничего не проверив
  без customAlias — иначе 409 прилетит от проверки занятого алиаса, то есть
    от совсем другого механизма

Ассерты:
  repository.count() == 1                      — claim-first сработал
  idempotencyRecordRepository.count() == 1
  bodies.distinct().count() == 1               — все дождались ответа победителя
  statuses.distinct() == [201]                 — в отчёте видно [201, 409]

--- 6. Thread.currentThread().interrupt() — зачем ---

Прерывание в Java КООПЕРАТИВНОЕ: interrupt() всего лишь поднимает булев флаг
на объекте Thread. Убить поток снаружи нельзя.

КЛЮЧЕВОЕ: sleep/wait/join при выбросе InterruptedException СБРАСЫВАЮТ флаг
в false. Логика JDK — исключение и есть способ доставки сигнала, раз доставлен,
флаг не нужен. Значит внутри catch поток снаружи выглядит НЕпрерванным.

Поймал и не восстановил -> сигнал УНИЧТОЖЕН, не "потерян в логе".
Кто наверху его ждёт:
  ExecutorService.shutdownNow() — воркер спокойно возьмёт следующую задачу,
    awaitTermination отвалится по таймауту
  graceful shutdown Tomcat — поток запроса продолжит работать, остановка висит
  while (!Thread.currentThread().isInterrupted()) выше по стеку не выйдет
  Future.cancel(true) не отменит

Обёртка в RuntimeException НЕ заменяет восстановление: исключение летит по
стеку вызовов, флаг живёт на объекте Thread. Фреймворк смотрит isInterrupted(),
а не разбирает твои исключения.

Два правильных варианта:
  пробросить InterruptedException дальше (тогда флаг не нужен)
  восстановить флаг + бросить unchecked — когда сигнатуру менять нельзя

Ловушка: Thread.interrupted() (статический) проверяет И СБРАСЫВАЕТ,
         thread.isInterrupted() (экземплярный) только проверяет.

Задача. Разбить links на нативное Postgres hash-партиционирование по short_code (4 партиции), с миграцией и проверкой partition pruning.
Миграция. Перевести существующую таблицу в партиционированную «на месте» нельзя — ALTER TABLE ... PARTITION BY не существует. Схема: переименовать старую (RENAME TO links_old),
 создать новую с PARTITION BY HASH (short_code), создать 4 партиции через FOR VALUES WITH (MODULUS 4, REMAINDER 0..3), перелить данные INSERT ... SELECT, после проверки
  дропнуть старую.
Генерация DDL существующей таблицы. Встроенного SHOW CREATE TABLE в Postgres нет. Способы: pg_dump --schema-only --table=... (канонично), psql \d+ (структура, но не готовый DDL),
 в DBeaver — вкладка DDL в редакторе таблицы или правый клик → Generate SQL → DDL.
OVERRIDING SYSTEM VALUE. Разрешает вручную вставить значение в колонку GENERATED ALWAYS AS IDENTITY (иначе — ошибка). Нужно, чтобы сохранить старые id при переливке.
Для bigserial/BY DEFAULT не требуется.
setval(pg_get_serial_sequence(...), max(id)). После ручной вставки id последовательность не двигается и выдаст конфликтующие значения. pg_get_serial_sequence находит имя
последовательности, setval синхронизирует её с реальным максимумом. Тонкость: третий аргумент is_called (по умолчанию true → следующий = max+1); на пустой таблице корректнее
передавать его явно.
Проверка pruning. EXPLAIN (ANALYZE) SELECT * FROM links WHERE short_code = '...' должен показать скан одной партиции, а не Append по четырём. Hash-pruning работает только на
равенстве (=) с константой/параметром — для lookup по short_code это идеально. Для prepared statements — runtime pruning (Subplans Removed: N).
Проверить enable_partition_pruning = on.
Ключевая проблема — уникальные ключи. На партиционированной таблице любой PK/UNIQUE обязан включать колонку партиции. В исходной схеме были два независимых одноколоночных ключа: PRIMARY KEY (id) и UNIQUE (short_code).
Партиция по short_code → ломается PRIMARY KEY (id).
Партиция по id → ломается UNIQUE (short_code).
Куда ни партиционируй — один constraint падает. Это структурное ограничение, не обходится настройкой.
Итоговое решение. id в этой схеме избыточен. short_code — естественный PK: уже уникален, ключ поиска и ключ партиции одновременно. Финальная таблица — PRIMARY KEY (short_code),
 PARTITION BY HASH (short_code), без id. Перед удалением id проверить: нет ли FK на него из других таблиц, не капризничает ли ORM без числового PK, не нужен ли монотонный
 порядок (закрывается created_at).
Индексы. Неуникальный CREATE INDEX (напр. на long_url) работает нормально — становится partitioned index с локальной копией на каждой партиции. Ограничение «включать ключ
партиции» касается только PK/UNIQUE.
